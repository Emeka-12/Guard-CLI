## Summary

Three `analyzer` correctness fixes around scan entry points and inline suppressions, plus
one `checks` refactor. One commit per issue (plus a docs commit for #408).

## Changes

### #406 - `scan_files` diverged from `scan_directory`

`scan_files` was public, documented as "same convention as `scan_directory`", but took no
`includes`, never skipped generated files, never deduped, and did not filter by extension.

- Extracted the shared per-file filter into `classify_rust_path` (`.rs` extension -> exclude
  globs -> include globs -> generated-file header), returning a `PathVerdict`
  (`Scan` / `GeneratedSkip` / `Reject`). Both `collect_rust_paths` and `scan_files` now run
  through it, so there is one copy of the rule instead of a fourth.
- Extracted `compile_globs` so every entry point compiles exclude/include patterns the same
  way.
- `scan_files` now takes `includes: &[String]`, applies the generated-file skip, calls
  `dedup_findings`, and returns `(findings, files_scanned, files_skipped)`.
- Doc comment rewritten to state the one remaining difference from `scan_directory` (it does
  not walk a directory).
- New test `scan_files_matches_scan_directory_findings_and_filters_generated` asserts the
  findings themselves match `scan_directory` and that a `// @generated` file is counted in
  `files_skipped`, not scanned. The existing count test is updated for the new signature and
  the new `includes` parameter.

### #408 - inline suppression silently lost when a blank/comment/attribute line intervenes

`parse_suppressions` looked only at `idx + 1`, so `// soroban-guard: allow(...)` above a
blank line, a `///` doc comment, or a `#[allow(...)]` attribute bound to that line (which no
finding is ever reported on) instead of the method below it.

- Added `next_substantive_line`, which skips blank lines, `//` / `///` / `//!` comments, and
  `#[...]` / `#![...]` attribute lines to find the first line of real code, and bound the
  suppression to that.
- The line-level case (annotation directly above a non-`fn` statement) is unchanged.
- Tests for the attribute, blank-line, and doc-comment forms, plus a regression test that a
  suppression directly above a `let` stays line-level.
- `docs/false-positives.md` now documents the skip-forward rule.

### #409 - `function_name_from_line` matched `"fn "` anywhere in a line

The function target was derived by scanning the raw text of the following line for the
substring `"fn "`, which matches string literals (`"call fn later"` -> name `later`),
comments, and type positions (`let f: fn(u32)`), registering function-scoped suppressions
for nonexistent names.

- `parse_suppressions` now resolves the target from `build_fn_spans` - the exact
  `(impl_type, function_name, start_line, end_line)` tuples parsed from the `syn::File` -
  by matching `start_line` to the line following the annotation, and falls back to a
  line-level suppression when no method starts there.
- Deleted `function_name_from_line`; it had no other callers.
- Tests: a `fn`-containing string literal and a `fn(u32)` type annotation on the line after
  a suppression comment register no function-scoped suppression.

### #422 - four identical `receiver_chain_contains_*` helpers in `util.rs`

`receiver_chain_contains_storage` / `_events` / `_temporary` / `_persistent` were
byte-for-byte identical apart from one method-name string.

- Added `receiver_chain_contains(expr, method)` holding the single traversal.
- The four names are kept as one-line wrappers, so the ~15 call sites across the checks
  crate are untouched.
- New test `receiver_chain_contains_walks_a_nested_chain` exercises the shared walk over
  `env.storage().persistent().get(&key)`.
- Out of scope: `crates/checks/src/panics.rs` has its own private fifth copy of this walk;
  the issue scopes to the four in `util.rs`, so it is left alone.
